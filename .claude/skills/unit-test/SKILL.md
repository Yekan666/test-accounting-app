# 单元测试技能

## 何时使用

- 用户要求为代码编写单元测试
- 用户要求执行已有测试并给出测试报告
- 修改代码后想验证是否影响现有功能

## 测试范围规则

**优先测试（无外部依赖的纯函数）：**
- `src/utils/` 下的工具函数（如 categories.ts）
- 其他不依赖 Tauri 插件、数据库、浏览器环境的函数

**默认不测试（需要特殊环境，告知用户后跳过）：**
- `src/db/database.ts` — 依赖 tauri-plugin-sql，只能在应用运行时执行，Node 测试环境跑不了
- React 组件 — 需要 jsdom + @testing-library 额外环境，当前项目未配置

## 步骤

### 第一步：分析代码，找出可测函数

- 阅读 `src/` 下的源文件
- 找出输入输出明确的纯函数（无外部依赖、相同输入必有相同输出）
- 列出待测试函数清单

### 第二步：编写测试文件

- 测试文件放在**被测文件同目录**，命名为 `<文件名>.test.ts`
  （例如 `src/utils/categories.ts` 的测试是 `src/utils/categories.test.ts`）
- 用 `describe`（分组）+ `it`（单个测试）组织用例
- 每个函数至少覆盖：
  1. **正常情况**：典型输入，验证期望输出
  2. **边界情况**：空输入、极限值、无匹配项
  3. **异常情况**：应报错的输入（用 `expect(...).rejects.toThrow()` 等）
- 用中文描述测试用例，例如 `it("没有自定义分类时，只返回系统预设分类")`
- 遵循被测代码的命名与风格

### 第三步：执行测试

```bash
npm test
```

- 若失败，阅读失败详情（哪个文件、哪个测试、期望值与实际值），**修复测试或报告问题**，不掩盖失败
- 若用户要求只跑某个文件：`npx vitest run <文件名>`

### 第四步：输出测试报告（终端文字）

按以下格式向用户汇报：

```
## 📋 单元测试报告

- 测试文件：N 个
- 测试用例：N 个，全部通过 ✅（或 X 个失败 ❌）

失败详情（如有）：
- 文件 / 测试名：期望 xxx，实际得到 yyy
```

- 全部通过 → 明确说"全部通过"
- 有失败 → 列出每个失败的原因，并给出处理建议

## 注意事项

- 测试必须真实运行，**不能编造测试结果**；`npm test` 的输出就是唯一事实来源
- 不要修改被测业务代码去"迁就"测试；发现测试暴露的问题时，先报告用户，由用户决定是否修复
- 新增功能代码时，可主动建议补充对应测试
