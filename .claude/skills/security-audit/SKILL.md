# 安全审计技能

## 何时使用

- 用户要求检查代码安全性 / 安全审计
- 项目存档、推送 GitHub、发布前，建议先做一次安全审计

## 检查范围

整个项目（含隐藏文件），重点关注：

- `src/` 下所有 `.ts` / `.tsx` 代码
- `src-tauri/`（Rust 后端、Tauri 配置、权限配置）
- 配置文件：`tauri.conf.json`、`package.json`、`vite.config.ts`、`.gitignore`、`src-tauri/capabilities/` 等
- `.env` 类文件（若存在）
- git 提交历史中的敏感信息（可选用 `git log -p` 检查）

## 四类检查项

### 1️⃣ 代码中的敏感信息泄露

用 Grep 搜索以下模式（含大小写变体）：

- `password`、`passwd`、`pwd =`、`密码`
- `token`、`api[_-]?key`、`apikey`、`secret`、`private[_-]?key`、`access[_-]?key`
- 已知令牌特征前缀：`ghp_`（GitHub）、`sk-`（OpenAI 等）、`AKIA`（AWS）、`-----BEGIN (RSA|EC|OPENSSH) PRIVATE KEY-----`（私钥块）
- 硬编码连接串：`mysql://`、`postgres://`、`mongodb://` 带用户名密码的 URL

判定规则：

- 变量名是 token/password 但值是空串、占位符（`xxx`、`your_key`）、环境变量引用（`process.env.X`）→ **不算泄露**
- 值是真实形态的密钥（一长串随机字符、密钥块）→ **算泄露**
- 注释里贴的示例密钥 → 算泄露，按最低严重度提示删除

### 2️⃣ SQL 注入等注入漏洞

- 找到所有 SQL 语句（`SELECT/INSERT/UPDATE/DELETE`），检查写法：
  - **安全**：参数化写法（`?` 占位符 + 参数数组），如 `db.execute("SELECT * FROM records WHERE id = ?", [id])`
  - **危险**：字符串拼接用户输入（`WHERE id = ${id}`、`+ id +`、`format()/模板字符串` 把变量直接拼进 SQL）
- 用户输入包含：表单值、搜索词、URL 参数、外部传入的任何字符串
- 其他注入面：
  - 命令注入：`child_process` / `Command` 执行拼接的用户输入
  - 路径注入：用户输入直接拼文件路径
  - XSS：`dangerouslySetInnerHTML`、`innerHTML` 直接渲染用户输入

### 3️⃣ 配置文件明文敏感信息

逐个读取配置文件，检查：

- `tauri.conf.json`：有无硬编码密钥、令牌
- `package.json`：scripts 里有无内嵌令牌（如 `GITHUB_TOKEN=xxx npm publish`）
- `src-tauri/capabilities/*.json`（若存在）：权限是否过宽（见第 4 类）
- `.gitignore`：`.env`、`*.pem`、`*.key`、凭据文件是否被忽略（没忽略 → 提示补充）
- settings 类文件：无（有就检查，但项目配置类本地文件若被 gitignore 忽略则告知用户即可）

### 4️⃣ 其他安全隐患

- **Tauri 权限过宽**：`capabilities` 允许的插件权限是否超出实际需要（如允许了不用的核心权限）
- **XSS**：`dangerouslySetInnerHTML` / `innerHTML` / `v-html` 的使用位置及输入来源
- **网络请求**：`fetch` / `axios` 是否用明文 http 发送敏感数据
- **依赖安全**：可提示运行 `npm audit`（需要网络，作为可选建议，不强制）
- **git 历史泄露**：`git log -p` 搜密码/token 模式（如确认历史里有真实密钥，提示用户该密钥已不可信，应作废轮换）

## 工作流程

### 第一步：确定范围并扫描

- 用 Glob 列出项目文件，Grep 搜敏感模式
- 对命中的位置用 Read 打开上下文确认是否真泄露

### 第二步：SQL / 注入面检查

- 定位所有 SQL 语句（`src/db/database.ts` 等），逐条判定参数化或拼接
- 检查其他注入面（命令、路径、XSS）

### 第三步：配置文件检查

- 逐个读取并核对（见第 3 类检查项）

### 第四步：输出安全审计报告

按以下格式汇报：

```
🔒 安全审计报告
- 审计范围：<文件清单>
- 发现问题：N 个（高危 X / 中危 Y / 低危 Z）

【高危】<文件>:<行号> —— <问题类型>
  现状：<引用原文（敏感值打码）>
  风险：<通俗说明会被怎样利用、后果是什么>
  建议：<具体修复方案>

【中危】...
【低危】...

✅ 未发现问题的部分：<说明哪些项检查过且安全>
```

严重度分级：

- **高危**：真实密钥泄露、SQL 注入可被利用、私钥泄露——必须处理
- **中危**：潜在注入风险、配置权限过宽、.gitignore 未忽略敏感文件
- **低危**：注释中的示例密钥、可改进项

### 第五步：修复（可选，需用户确认）

- 报告完成后**询问用户**是否修复
- 用户同意后：只做安全修复，不顺手改其他代码；修复后复检确认问题消除

## 注意事项（重要）

- **敏感值打码**：报告中引用泄露的密码/令牌时，只显示前 4 位和后 2 位（如 `ghp_******eA`），**绝不输出完整密钥**——完整密钥出现在对话里本身也是二次泄露
- **git 历史泄露**：若确认历史提交中有真实密钥，告知用户：密钥必须作废并重新生成（改代码删除只是第一步，密钥本身已不可信）
- 以真实扫描结果为准，不编造、不夸大；检查过的项要如实报告
- 不擅自修改代码；修复需用户确认后执行
- 报告全部用中文，让不懂编程的用户也能看懂风险
