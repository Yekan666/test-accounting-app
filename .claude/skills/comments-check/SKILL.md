# 注释检查技能

## 何时使用

- 用户要求检查代码注释质量 / 审查注释
- 新功能开发完、存档前，希望确认注释是否齐全

## 三条检查标准（核心要求）

### 1️⃣ 注释完整性：该有的注释有没有？

以下代码必须有注释，缺了记为"缺少注释"问题：

- **每个函数**（含箭头函数、React 组件函数）：函数前应有注释，说明
  - 这个函数是干什么的（作用）
  - 每个参数是什么含义
  - 返回值是什么
  - 注意事项（如：会修改哪个数据、依赖什么前提条件）
- **重要核心代码**，包括但不限于：
  - 数据库增删改查（SQL 操作）
  - 复杂条件分支 / 多重校验逻辑
  - 状态更新、副作用（useEffect）
  - 数据转换、格式化、计算逻辑
  - 容易踩坑的地方（如边界判断、特殊处理）
- 特别提醒：**只给内部逻辑写注释、却不给函数写头注释**，也算不完整

### 2️⃣ 注释准确性：注释和代码一致吗？

逐条核对注释描述与代码实际行为：

- 注释描述的作用 ≠ 代码实际做的事 → 记为"注释不匹配"
- 注释声称的参数/返回值/错误情况与函数签名不一致 → 记为"注释不匹配"
- 注释含糊其辞（"做一些处理"、"后面再说"）没有说清实际行为 → 记为"注释不匹配"
- 代码改了，注释没跟着改（陈旧注释）→ 记为"注释不匹配"

### 3️⃣ 小白视角：注释看得懂吗？

- 用通俗语言，避免堆砌专业术语（术语出现时应顺带解释）
- 说清"为什么这么做"，而不只是"做了什么"
- 避免空洞注释（如 `// 增加 x` 这种只是复述代码的注释，没增加信息量）
- 注释描述应该让完全不了解这段代码的人能理解意图

## 工作流程

### 第一步：确定检查范围

- 默认检查 `src/` 下全部 `.ts` / `.tsx` 文件（Glob 列出文件清单）
- 用户指定文件时：只检查指定文件，并在报告中注明范围

### 第二步：逐文件阅读

- 用 Read 通读每个文件，对照代码与注释
- 对每个函数 / 核心代码块，按三条标准逐条过一遍

### 第三步：生成问题清单

对每个问题记录：

| 项目 | 说明 |
|------|------|
| 位置 | 文件路径:行号 |
| 类型 | 缺少注释 / 注释不匹配 / 不够通俗 |
| 问题描述 | 现状是什么、为什么不符合标准 |
| 建议 | 怎么写才合格（给出具体示例，中文） |

### 第四步：输出检查报告

按以下格式汇报：

```
📋 注释检查报告
- 检查范围：<文件清单或说明>
- 问题总数：N 个（缺少注释 X 个 / 注释不匹配 Y 个 / 不够通俗 Z 个）

【问题明细】
1. <文件>:<行号> —— <类型>
   现状：<原文引用>
   问题：<为什么不合格>
   建议：<具体修改示例>

✅ 做得好的地方（如有）：<列出合格的注释示例>
```

### 第五步：修复（可选，需用户确认）

- 报告完成后**询问用户**是否要修复（补充 / 修改注释）
- 用户同意后：只修改注释，**绝不修改业务代码**；修复后重新运行检查确认问题清零

## 注意事项

- 以真实代码为准，不编造问题、不夸大问题；没问题的文件如实说"合格"
- 只处理注释，**禁止修改任何业务代码**（哪怕是顺手修正代码问题，也要单独报告给用户决定）
- 判断"注释是否匹配"时以函数签名、代码逻辑、数据流向为唯一依据
- 报告全部用中文，措辞让不懂编程的用户也能看懂
- 修复注释后应复检一遍，确认没有引入新的"注释不匹配"
